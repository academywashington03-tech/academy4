# دليل إعداد Supabase وقاعدة البيانات

> **الحالة:** ملفات قاعدة البيانات مكتوبة، لكنها **لم تُشغَّل على Supabase حقيقي قط**، واختبارات SQL (176 تأكيداً) **لم تُنفَّذ**. هذا الدليل خطة؛ لا تعتبر أي خطوة ناجحة قبل أن تراها تنجح.
> هذه الوثيقة هي المرجع الحالي، وتحلّ محل الوثيقة التاريخية `02-supabase-setup-and-first-admin.md`.

## ما الذي ينشئه المشروع في Supabase (حسب الملفات الفعلية)

الإجمالي المحسوب من الملفات: 27 جدولاً (كلها RLS مفعّل)، 42 دالة، 55 سياسة، مشغّلان على `auth.users` وآخران على `profiles` و`courses`.

## الخطوة 1 — أنشئ مشروعاً
1. supabase.com ← Sign in ← **New project**. اختر أقرب منطقة متاحة لمستخدميك (مصر).
2. ضع كلمة مرور قوية لقاعدة البيانات **واحفظها في مدير كلمات مرور**. (لن يعرضها Supabase لاحقاً.)
3. الخطة المجانية كافية للتجربة. **حدودها حسب صفحة الأسعار الرسمية (فُحصت 14 أكتوبر 2026):** قاعدة 500 ميغابايت، تخزين 1 غيغابايت، أقصى رفع للملف 50 ميغابايت، خروج بيانات 5 غيغابايت، **إيقاف تلقائي بعد أسبوع بلا نشاط، ولا نسخ احتياطي تلقائي**.

## الخطوة 2 — شغّل ملفات الترحيل (بالترتيب)
**متطلبات البيئة:** الملفات تفترض مشروع **Supabase** (وليس PostgreSQL خاماً): مخطط `auth` (`auth.users`, `auth.uid()`)، ومخطط `storage` (`storage.buckets`, `storage.objects`)، والأدوار `anon` و`authenticated`، وPostgreSQL 13 أو أحدث (لـ`gen_random_uuid()` المدمجة). الملف 0001 ينشئ `pgcrypto`. **ترتيب التنفيذ إلزامي:** 0001 → 0011، ثم اختبارات `supabase/tests` على قاعدة **تجريبية** فقط عبر `npm run test:sql -- --migrate` (يشغّل الترحيلات ثم الاختبارات بترتيب: rls ثم phase5 … phase11 ثم phase13).

في Supabase: **SQL Editor ← New query**، ثم لكل ملف من `supabase/migrations/` **بالترتيب 0001 ثم 0002 … حتى 0011**:
1. افتح الملف من المشروع، انسخ **محتواه كاملاً**، والصقه في المحرر.
2. اضغط **Run**. المتوقع: «Success» بلا أخطاء.
3. **توقف عند أول خطأ**، ولا تكمل للملف التالي، وأرسل لي نص الخطأ كاملاً ورقم الملف.

⚠️ الملفات **ليست مصمَّمة لإعادة التشغيل** (بعض الأوامر تفشل إن كان الكائن موجوداً). إن فشل ملف في منتصفه فالأسلم إنشاء مشروع جديد فارغ والبدء من 0001.
⚠️ إن فشل إنشاء سياسات `storage.objects` بخطأ صلاحيات في 0002 أو 0005، فأرسل لي الخطأ لنُنشئها من Storage ← Policies بالمنطق نفسه. **لا أستطيع الجزم الآن إن كان محرر SQL يسمح بها.**

### تحقق بعد التشغيل (بعينك)
- Table Editor يعرض الجداول الـ27 وأمام كل منها «RLS enabled».
- Storage يعرض ثلاثة مخازن: `course-resources` (Private) و`course-covers` (Public) و`payment-receipts` (Private).
- Authentication ← Users: لا مستخدمين بعد.

## الخطوة 3 — اضبط المصادقة (Authentication)
- **URL Configuration:** `Site URL` = رابط موقعك. و`Redirect URLs` أضف: `<رابطك>/auth/callback` (يُستخدم لتأكيد البريد واستعادة كلمة المرور). للتجربة المحلية أضف أيضاً `http://localhost:3000/auth/callback`.
- **Email:** فعّل «Confirm email». الكود يوجّه المسجَّل الجديد لرسالة «افتح الرابط لتفعيل الحساب».
- **قوالب البريد:** الصق القالبين من `docs/email-templates/` (تأكيد التسجيل، استعادة كلمة المرور) وبدّل `YOUR-DOMAIN` برابطك.
- **SMTP مخصص:** متاح في الخطة المجانية حسب صفحة الأسعار. قبل أي إطلاق اضبط SMTP خاصاً بنطاقك؛ حدود البريد المدمج لم أتحقق منها.
- ⛔ **لا تفعّل CAPTCHA في Supabase.** الكود الحالي **لا يرسل رمز CAPTCHA** مع التسجيل أو الدخول، فتفعيله سيمنع كل تسجيل ودخول. (الحماية الحالية: تحديد معدل داخل التطبيق + حدود Supabase.)
- **Google (اختياري):** فعّل Google في Providers وفق إرشادات Supabase، ثم اضبط `NEXT_PUBLIC_GOOGLE_ENABLED=1` وأعد النشر. لم يُختبر.

## الخطوة 4 — انسخ مفاتيح الاتصال
من لوحة المشروع (Project Settings ← API؛ قد تختلف أسماء القوائم): انسخ إلى متغيرات البيئة:
| في Supabase | اسم المتغير في المشروع | ملاحظة |
|---|---|---|
| Project URL | `NEXT_PUBLIC_SUPABASE_URL` | عام |
| anon / public key | `NEXT_PUBLIC_SUPABASE_ANON_KEY` | يظهر في المتصفح بتصميمه؛ تحميه سياسات RLS |
| service_role key | `SUPABASE_SERVICE_ROLE_KEY` | **سري جداً: يتجاوز كل الحماية. لا تضعه في أي ملف كود ولا في الدردشة** |

> إن عرضت لوحة Supabase أنواع مفاتيح بأسماء جديدة، فالمشروع مكتوب لمفتاحي anon وservice_role. إن لم تجدهما فأخبرني بما تراه؛ لم أتحقق من هذه النقطة.

للتحقق دون كشف القيم: `node scripts/check-env.mjs` (يقول SET/missing فقط).

## الخطوة 5 — أنشئ المدير الأول (الوحيد الممكن)
لا أحد يصبح مديراً من التسجيل العام (مشغّل قاعدة البيانات يجبر كل حساب جديد على «طالب»).
1. سجّل من صفحة `/register` بالبريد الذي سيكون للمدير، وأكّد بريدك.
2. في SQL Editor شغّل (بدّل البريد):
```sql
update profiles set role = 'super_admin'
where id = (select id from auth.users where email = 'بريدك@example.com');
```
3. سجّل الدخول وافتح `/admin`. إن ظهر «ليست لديك صلاحية» فراجع أنك أكّدت البريد وأن السطر المحدَّث ظهر في النتيجة (`UPDATE 1`).
فعّل المصادقة الثنائية على حسابك في Supabase وعلى بريد المدير.

## الخطوة 6 — فعّل الدفع اليدوي والإعدادات (اختياري)
من `/admin/settings`: تفعيل الدفع اليدوي وتعليماته، وبيانات الأكاديمية، واسم الموقّع على الشهادة. تُحفظ في الجدول `settings` بالمفاتيح `public.manual_payments` و`public.academy` و`public.certificate`.

## الخطوة 7 — شغّل اختبارات SQL (على مشروع تجريبي منفصل)
أنشئ مشروعاً مجانياً ثانياً **للتجارب فقط** (لا تستخدم مشروعك الحقيقي)، ثم من جهاز فيه `psql`:
```bash
DATABASE_URL="postgresql://postgres:كلمة_المرور@db.<مشروع>.supabase.co:5432/postgres" ./scripts/run-sql-checks.sh --migrate
```
(`DATABASE_URL` من Project Settings ← Database ← Connection string. **لا تحفظه في ملف داخل المشروع.**)
- يطبّق الترحيلات ثم يشغّل 8 ملفات: `rls_checks` و`phase5…phase11_checks`. كل ملف داخل معاملة تُلغى (لا يترك بيانات). يُنشئ مخططاً مؤقتاً باسم `tst` ومستخدمين وهميين داخل المعاملة.
- النجاح = تظهر عبارات `PASS` وتنتهي الرسالة بـ `ALL SQL CHECKS PASSED`. أي فشل يظهر كخطأ `assert`: أرسله لي.
- **لم يُشغَّل أي منها حتى الآن.** هذه الاختبارات هي ما يثبت أن منطق الدفع والصلاحيات يعمل داخل قاعدة البيانات.

## الصيانة
- **النسخ الاحتياطي:** الخطة المجانية بلا نسخ تلقائي؛ Pro فيها نسخ يومي يُحفظ 7 أيام (حسب صفحة الأسعار). استرجاع نقطة زمنية (PITR) إضافة مدفوعة.
- **الإيقاف التلقائي:** المشروع المجاني يُوقَف بعد أسبوع بلا نشاط. استأنفه من لوحة Supabase. Pro لا يُوقَف.
- **تحديثات لاحقة:** أي ملف ترحيل جديد (0012…) يُشغَّل مرة واحدة بالترتيب بعد أخذ نسخة احتياطية.
- **حذف حساب بطلب صاحبه:** أوقف الحساب أولاً من `/admin/students`، ثم احذف المستخدم من Authentication ← Users. تنبيه: الطلبات المالية مرتبطة بقيد منع الحذف، فقد يلزم إجراء يدوي لإخفاء الهوية. وضع سياسة احتفاظ مكتوبة مسؤوليتك.

## مشاكل شائعة
| العرض | السبب والحل |
|---|---|
| `relation "…" already exists` | أُعيد تشغيل ملف سبق تشغيله؛ لا تعيده |
| `permission denied for schema storage` | سياسات التخزين: أرسل الخطأ لنُنشئها من لوحة Storage |
| بعد التسجيل لا يصل بريد | SMTP غير مضبوط أو قيود البريد المدمج؛ اضبط SMTP مخصصاً |
| `registration closed` / «التسجيل مغلق» | أُغلق التسجيل من `/admin/settings`؛ أعد تفعيله |
| المشروع لا يستجيب | قد يكون موقوفاً بسبب الخمول (الخطة المجانية) |
